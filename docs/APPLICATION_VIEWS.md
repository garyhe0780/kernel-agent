# Application navigation and saved views

Application definitions can contain `navigation`, `views`, and `startView`. They are generated by the agent, editable in **Change application → Navigation and saved views**, and published through the existing draft/version/migration flow. Older definitions default to all records and one navigation section per entity.

- `navigation`: every entity exactly once, in display order, with a business-facing label. An empty list uses entity order and pluralized labels.
- `navigation[].icon` (optional, application contract v9): a semantic icon key. Supported values are `purchase`, `organization`, `contact`, `people`, `deal`, `project`, `task`, `issue`, `payment`, `ticket`, `activity`, `milestone`, `asset`, `order`, `document`, `audit`, and `records`. Omit it to infer an icon from the stable entity type. Display labels may be renamed or translated without changing the icon. Generic party directories use organizations by default, with known people aliases using people; use an explicit override for other roles. Unknown entity types use neutral records. These are validated keys, not SVG markup, remote URLs, or imports.
- `views`: at most 24 named views, each with a stable application-local ID and one entity.
- `filters`: at most six AND conditions. `eq` uses typed equality; `lte` and `gte` accept integer fields. Field types, enum values and bounds are validated. Relationship filters are not supported.
- `sort`: a non-relationship field or `$createdAt`, ascending or descending. Missing values sort last; record IDs break ties. Default is newest first.
- `columns`: up to eight known unique fields including `title`. Empty uses the renderer's default table. Relationships can be displayed as columns.
- `startView`: an existing view ID, or null for all records in the first section.

Published snapshots namespace entity references by application while retaining local view IDs. The shared workbench renders section labels/order, nested saved views and scoped counts. Search and lifecycle filters narrow the active saved view. Selecting All records clears that view; reloading reopens the published starting view. Temporary selection is not bookmarked in the URL.

Saved views organize records; they are not authorization boundaries. Existing workspace, application and action checks remain authoritative. The current renderer filters the scoped snapshot in memory; server-side pagination and large-dataset queries are future work.

Presentation-only publications retain existing records and capability versions, and do not invalidate pending proposals. Migration previews show navigation, view and starting-view differences. Definitions and metadata are retained in application version history.

The sidebar and application mark share a bounded Lucide icon registry. Purchase requests use a cart, suppliers and customer organizations use a building, and review uses a clipboard check. Contacts, deals, tasks, activities, issues, projects, payments and support tickets have distinct domain icons. The application mark and workspace favorites use the published starting entity (or the first navigation entity), so their icon remains stable while visiting other queues. Kernel workspace branding remains separate. Existing applications receive these defaults when their presentation is read; no database migration or republication is required. Custom definition authors can override a navigation item, for example `{ "entity": "equipment", "label": "Equipment", "icon": "asset" }`. Icon-only edits appear in migration previews and use the existing presentation publication flow.

Verification includes purchasing and CRM definitions, invalid filters/navigation/defaults, typed numeric sorting, a mocked agent validation-repair cycle, and an integration test publishing a view-only change while preserving a record and an applicable pending proposal. Browser verification used the synthetic Team purchasing workspace; live model generation was not connected.
